# RFC 0001: T:cap shape + canonical error codes

**Author:** jakeliu
**Date:** 2026-05-24
**Status:** Draft
**Target version:** v0.2

---

## Summary

v0.2 adds two cross-harness conventions that emerged from the 25-harness mesh
demonstrator (24 ML + 1 software + 1 hardware): a standardized `T:cap` packet
shape for capability discovery, and a canonical registry of `ERR_*` codes that
harnesses must use instead of inventing their own. Both are zero-breaking
for v0.1 parsers — slot grammar is unchanged.

## Motivation

After building 25 harnesses each with a `*.capabilities` verb and ~12 distinct
error conditions (`ERR_NOT_CAPABLE`, `ERR_NEEDS_CREDENTIALS`, `ERR_OOB`, etc.),
two problems became visible:

1. **Capability discovery is ad-hoc.** Each harness's `capabilities` verb
   returns a different `O:{...}` shape. An orchestrator LLM that wants to ask
   "what can this harness do?" must learn each harness's schema. With 25
   harnesses today and the 24-method orchestrator vision, that scales badly.

2. **Error codes drift.** Three harnesses use `ERR_NOT_FOUND`. Two use
   `ERR_404`. One uses `entity_not_found`. The runner can't write generic
   recovery logic without a canonical list.

Evidence: log corpus at `~/.mllang-shim/test_log.jsonl` shows 374 successful
test packets across 25 harnesses; pattern-mining for error codes returned 14
distinct strings for 7 conceptually identical conditions.

## Detailed design

### Change 1 — `T:cap` packet shape

A new packet **type** identifier in the `T:` slot signals capability discovery
output. The receiver is expected to emit a packet with `T:cap` and a structured
`CAP:` payload listing verbs, status, and constraints.

#### Before (v0.1, ad-hoc)

Each harness returns its own dict:

```
V:0.1.r1; I:c1; G:{}; N:"@ML_CLF -> ml.capabilities"; H:done; P:0.95;
O:{ok:true, tool:ml.capabilities, id:@ML_CLF, method_family:supervised_classifier,
   algorithm:tfidf+logistic_regression, verbs:[clf.predict, clf.train, ...],
   sklearn_version:1.6.1, ...};
```

#### After (v0.2, T:cap)

```
V:0.2.r1; I:c1; G:{}; T:cap;
N:"@ML_CLF -> ml.capabilities"; H:done; P:0.95;
CAP:{
  agent_id: @ML_CLF,
  family: supervised_classifier,
  algorithm: tfidf+logistic_regression,
  verbs: [
    {name: clf.predict, required: [text], optional: [],   side_effects: false},
    {name: clf.train,   required: [],     optional: [texts,labels], side_effects: true},
    {name: clf.explain, required: [text], optional: [],   side_effects: false},
    {name: clf.status,  required: [],     optional: [],   side_effects: false},
    {name: clf.reset,   required: [],     optional: [],   side_effects: true}
  ],
  runtime: {sklearn:1.6.1, numpy:2.0.2},
  state: {trained: true, n_train: 16}
};
```

**Constraints on `CAP:`:**
- `agent_id` MUST match the harness's `@TARGET` identity
- `family` SHOULD use the v0.2 family enum: `supervised_classifier`, `regression`,
  `gradient_boosting`, `random_forest`, `logistic_regression`,
  `support_vector_machine`, `k_nearest_neighbors`, `clustering`,
  `anomaly_detection`, `time_series_forecasting`, `recommendation`,
  `computer_vision`, `ocr_document_understanding`, `speech_to_text`,
  `text_to_speech`, `graph_ml`, `bayesian_probabilistic`, `causal_inference`,
  `reinforcement_learning`, `optimization_constraint_solver`,
  `embedding`, `reranker`, `retrieval_augmented_generation`,
  `llm_foundation_model`, `os_software_gateway`, `hardware_gateway`
- `verbs[].name` MUST be addressable via `N:@target -> verb`
- `verbs[].side_effects` MUST accurately report whether the verb mutates state
- `runtime` is optional; include if reproducibility matters

### Change 2 — Canonical error codes

A receiver MUST surface errors with one of the codes below in the
error packet's `O:{err:"..."}` field. New codes are added by RFC; harnesses
SHOULD NOT invent ad-hoc codes outside this list.

```
ERR_NOT_CAPABLE         verb not in ALLOWED_VERBS, or domain mismatch
ERR_NOT_FOUND           entity / model / file referenced doesn't exist
ERR_NEEDS_CREDENTIALS   backend rejected request due to missing/bad auth
ERR_NEEDS_PAIRING       device discovered but requires user-confirmed pairing
ERR_DOMAIN_MISMATCH     entity_id belongs to wrong domain for this verb
ERR_BAD_URL             malformed/unsupported URL scheme
ERR_BAD_FORMAT          input file format unsupported by harness
ERR_BAD_IMAGE           image cannot be decoded
ERR_OOB                 numeric/coordinate value outside accepted range
ERR_SHAPE_MISMATCH      feature dimension doesn't match model
ERR_TOO_SHORT           input below MIN_LEN
ERR_TOO_LONG            input above MAX_LEN
ERR_TOO_SMALL           image / sample below minimum dimension
ERR_HA_HTTP             HomeAssistant returned non-2xx HTTP
ERR_HA_UNREACHABLE      HomeAssistant URL not reachable
ERR_HA_UNEXPECTED       HomeAssistant returned malformed response
ERR_BACKEND_UNAVAILABLE backend selected by env not installed / not running
ERR_KASA_DISCOVER_FAILED  python-kasa discovery threw
ERR_KASA_CALL_FAILED    python-kasa control call threw
ERR_TTS_BACKEND_UNAVAILABLE  no `say` / `espeak` on PATH
ERR_TTS_TIMEOUT         tts.synthesize exceeded 20s
ERR_TTS_FAILED          tts.synthesize returned non-zero rc
ERR_OCR_BACKEND_UNAVAILABLE  no tesseract sidecar available
ERR_STT_BACKEND_UNAVAILABLE  no whisper sidecar available
ERR_NOT_DIR             path expected to be a directory wasn't
ERR_NOT_READY           device discovered but status != CONTROL_READY
```

Format: `ERR_<UPPERCASE_SNAKE>`. Optional `: <human-readable detail>` suffix.

## Examples

### Example 1 — T:cap from supervised classifier

```
V:0.2.r1; I:cap-1; G:{}; T:cap;
N:"@ML_CLF -> ml.capabilities"; H:done; P:0.95;
CAP:{
  agent_id: @ML_CLF, family: supervised_classifier,
  algorithm: tfidf+logistic_regression,
  verbs: [
    {name: clf.predict,  required: [text],          side_effects: false},
    {name: clf.train,    optional: [texts,labels],  side_effects: true},
    {name: clf.explain,  required: [text],          side_effects: false},
    {name: clf.status,   side_effects: false},
    {name: clf.reset,    side_effects: true}
  ],
  runtime: {sklearn: 1.6.1, numpy: 2.0.2},
  state: {trained: true, n_train: 16}
};
```

### Example 2 — Error packet using canonical code

```
V:0.2.r1; I:p1; G:{entity_id: light.porch}; T:err;
N:"@HOME -> light.turn_on"; H:done; P:1.0;
O:{ok:false, err:"ERR_NEEDS_PAIRING", entity_id:light.porch,
   detail:"plug requires Matter commissioning before control",
   suggest:"call home.pair first"};
```

### Example 3 — Orchestrator using T:cap to route

```
V:0.2.r1; I:route-1; G:{question:"predict customer churn from features X"};
T:route;
N:"@ORCHESTRATOR -> route.dispatch"; H:done; P:0.9;
ROUTE:{
  candidates: [
    {agent_id:@ML_CLF,  family:supervised_classifier, score:0.78},
    {agent_id:@ML_GB,   family:gradient_boosting,     score:0.82},
    {agent_id:@ML_BAYES,family:bayesian_probabilistic,score:0.65}
  ],
  pick: @ML_GB,
  why: "highest score; supervised binary classification matches problem shape"
};
```

### Change 3 — Alternative `N:` encoding (added after Gemini interop tests)

Some LLM tokenizers (notably Gemini 2.5 Pro) rewrite unquoted `@<word>` patterns
in the `N:` slot to local-file paths, breaking routing. v0.2 introduces an
equivalent **map-form** encoding that is vendor-safe because the `@` token sits
inside a quoted dict value:

```
N:{agent:"@ML_CLF", verb:"clf.predict"}
```

Both forms parse identically. Receivers MUST accept either. Composers MAY use
either; for cross-vendor packets the map-form is RECOMMENDED.

## Backward compatibility

- v0.1 parsers ignore unknown slots (`T:`, `CAP:`, `ROUTE:`) — they parse the
  rest of the packet correctly. No parser break.
- Harnesses that don't emit `T:cap` are still valid; their `capabilities` verb
  remains free-form. v0.2 only **adds** a recommended convention.
- Error codes already in use (`ERR_NOT_CAPABLE`, `ERR_NEEDS_CREDENTIALS`, etc.)
  are grandfathered into the canonical list. Any harness using a non-canonical
  string MUST migrate or be flagged by the spec gate.

## Adoption / use case evidence

- 25 harnesses currently emit a `*.capabilities` verb informally. RFC formalizes.
- Phase 1 ship gate (240 tests) demonstrated capability discovery works. Phase 2
  production gate (125 tests) showed the same `capabilities` verb is the lowest-
  cost survey point. `T:cap` makes that survey machine-readable.
- Error code drift was caught during phase 2 fuzz tests. 14 distinct codes for 7
  concepts.

## Open questions

- ? Should `T:cap` be REQUIRED for all `*.capabilities` outputs in v0.2, or
  OPTIONAL with a `MAY` clause? Current draft says SHOULD.
- ? Should `family` enum live in spec, or in a separate `families.md` registry
  updatable without bumping spec version?
- ? Do we want `CAP.verbs[].cost_class` (cheap / medium / heavy)? Useful for
  orchestrator triage but adds 25 calibration decisions.

## Risks

- Premature `family` enum lock — adding a new ML family means a spec bump.
  Mitigation: registry approach (separate file, additive).
- Canonical error registry grows unbounded. Mitigation: every new code requires
  RFC.
